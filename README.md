# Update-Manga

เว็บแอปติดตามตอนใหม่ของมังงะที่ชอบ จากกลุ่มเว็บธีมเดียวกัน (slow-manga, go-manga, up-manga, tanuki-manga
และเว็บอื่นที่ใช้ธีม "mangareader" เดียวกัน) — ดูรายการที่อัปเดต อ่านในหน้าเว็บได้เลย มีแจ้ง `NEW!`
สำหรับตอนที่ยังไม่ได้กดอ่าน และตั้งค่าเพิ่ม/ลบเรื่องที่ติดตามได้

โค้ดเดิม (`bot.py`, ใช้ playwright ส่งแจ้งเตือนเข้า Telegram) ยังอยู่ในโฟลเดอร์หลักเหมือนเดิม
แต่ **เว็บแอปใหม่ส่งแจ้งเตือน Telegram เองได้แล้วในตัว** (ดูหัวข้อ "แจ้งเตือน Telegram" ด้านล่าง)
โดยใช้ข้อมูลชุดเดียวกับที่แสดงในเว็บ (`webapp/data/manga.json`) — แนะนำให้ใช้เว็บแอปแทน `bot.py`
ไปเลยเพื่อไม่ให้ข้อมูลสองชุดเพี้ยนกัน (`bot.py` อ่าน/เขียน `manga_list.txt` + `manga_db.json`
คนละไฟล์กับเว็บแอป ถ้าเพิ่ม/ลบเรื่องผ่านหน้า "ตั้งค่า" ของเว็บ `bot.py` จะไม่รู้ด้วย) จะยังเก็บ
`bot.py` ไว้เป็น reference หรือลบทิ้งก็ได้ แต่ไม่ควรรันทั้งสองพร้อมกันเพราะจะได้แจ้งเตือนซ้ำ

## รันทดสอบบนเครื่อง (dev)

เว็บแอปไม่ต้องใช้ playwright เลย ใช้ `webapp/requirements.txt` แทน `requirements.txt` ที่ root
(อันนั้นเป็นของ `bot.py` เดิม):

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r webapp/requirements.txt

cd webapp
python3 migrate.py      # ครั้งแรกครั้งเดียว: ย้ายข้อมูลจาก manga_list.txt / manga_db.json เดิม
python3 app.py          # เปิดที่ http://127.0.0.1:5050
```

## เข้าสู่ระบบ (login)

เว็บแอปมีหน้า login ในตัว (จำเครื่อง 90 วัน ไม่ต้อง login ซ้ำทุกครั้งแบบ Basic Auth) เปิดใช้โดยตั้งใน `.env`:

```
WEB_USERNAME=ชื่อผู้ใช้ที่ต้องการ
WEB_PASSWORD=รหัสผ่านที่ต้องการ
SECRET_KEY=<สุ่มด้วยคำสั่งด้านล่าง>
```

สร้าง `SECRET_KEY` ด้วย:

```bash
python3 -c "import secrets; print(secrets.token_hex(32))"
```

**ต้องตั้ง `SECRET_KEY` ให้คงที่เสมอ** ถ้าปล่อยว่างแอปจะสุ่มใหม่ทุกครั้งที่รีสตาร์ท ทำให้ทุกคน
หลุด login ต้องล็อกอินใหม่หมด — ถ้าปล่อย `WEB_USERNAME`/`WEB_PASSWORD` ว่างทั้งคู่ จะไม่มี login เลย
(ใช้ตอน dev บนเครื่องตัวเองได้ แต่ **อย่าปล่อยว่างตอน deploy ขึ้น VPS**)

ถ้าใช้ Caddy อยู่แล้ว **เอา `basic_auth` block ออกจาก Caddyfile ได้เลย** (ซ้ำซ้อนกับ login ของแอป)
เหลือแค่ HTTPS + reverse proxy พอ:

```
yourdomain.com {
    encode zstd gzip
    reverse_proxy 127.0.0.1:5050
}
```

## ผู้ใช้หลายคน / สิทธิ์ admin

`WEB_USERNAME`/`WEB_PASSWORD` ใน `.env` ใช้แค่ครั้งเดียวตอนแอปรันครั้งแรก เพื่อสร้างบัญชี **admin
คนแรก** ไว้ใน `webapp/data/users.json` (มีรหัสผ่านแบบ hash เก็บไว้ ไม่ใช่ plaintext) หลังจากนั้น
แก้ `.env` จะไม่มีผลกับ login อีก ต้องจัดการผ่านหน้าเว็บแทน

- **เรื่องในระบบ (catalog)** ใช้ร่วมกันทุกคน สแครปครั้งเดียว — แต่ **ติดตามเรื่องไหนบ้าง / อ่านไปถึงไหน
  แล้ว** แยกเป็นรายคน (`webapp/data/users/<username>/`)
- **เฉพาะ admin** เท่านั้นที่: เพิ่ม/ลบเรื่องออกจากระบบ (แท็บ "ตั้งค่า"), กดรีเฟรช, เพิ่มสมาชิกใหม่
  (กันไม่ให้เซิร์ฟเวอร์โดนถล่มจากหลายคนกดรีเฟรชพร้อมกัน)
- **ผู้ใช้ทั่วไป** เข้าไปที่แท็บ "เรื่องทั้งหมด" เพื่อเลือกติดตามเรื่องที่สนใจเอง (เลิกติดตามได้
  ทุกเมื่อ เรื่องยังอยู่ในระบบให้คนอื่นเห็นตามปกติ)
- แจ้งเตือน Telegram (ดูหัวข้อถัดไป) จะส่งเฉพาะเรื่องที่บัญชี admin ที่ตั้ง Telegram ไว้ติดตามอยู่เท่านั้น
- เพิ่มสมาชิกใหม่: login ด้วยบัญชี admin → แท็บ "ตั้งค่า" → หัวข้อ "จัดการสมาชิก"

## Deploy บน VPS

แอปนี้ต้องตั้ง `WEB_USERNAME`/`WEB_PASSWORD` ไว้ก่อนเปิดให้เข้าถึงจากอินเทอร์เน็ต (ดูหัวข้อด้านบน)
ไม่งั้นใครก็ตามที่รู้ IP/URL จะเพิ่ม-ลบรายการหรือดูรายการอ่านของเราได้ นอกจากนี้แนะนำอย่างใดอย่างหนึ่งเพิ่ม:

- วางหลัง Caddy/nginx พร้อม HTTPS (ดูตัวอย่าง Caddyfile ด้านบน), หรือ
- จำกัดด้วย firewall ให้เข้าได้เฉพาะ IP ของตัวเอง, หรือ
- เข้าผ่าน SSH tunnel / VPN เท่านั้น (ไม่เปิดพอร์ตสาธารณะเลย)

ขั้นตอน:

```bash
# 1. clone และติดตั้ง
git clone https://github.com/mee6262/Update-Manga /opt/Update-Manga
cd /opt/Update-Manga
python3 -m venv .venv
source .venv/bin/activate
pip install -r webapp/requirements.txt

# 2. migrate ข้อมูลครั้งแรก (ถ้ามี manga_list.txt/manga_db.json เดิม)
cd webapp
python3 migrate.py

# 3. รันด้วย gunicorn (ไม่ใช้ dev server ของ Flask ใน production)
../.venv/bin/gunicorn -k gthread -w 2 --threads 16 --timeout 300 app:app -b 127.0.0.1:5050
```

**ต้องใช้ `-k gthread --threads` เสมอ** — งานเกือบทั้งหมดของแอปนี้คือ "รอเน็ต" (พร็อกซีรูปจาก CDN
ต้นทาง, ดึงหน้าเว็บ) ไม่ใช่งานคำนวณ ถ้าใช้ worker แบบ sync 2 ตัวตามค่า default เซิร์ฟเวอร์จะรับได้
ทีละ 2 คำขอเท่านั้น พอเปิดอ่านตอนหนึ่งที่มีรูป 40-50 ใบ รูปจะต่อคิวกันยาวและทำให้ทั้งเว็บ (รวมถึง
คนอื่นที่ใช้อยู่พร้อมกัน) หน่วงตามไปด้วย ส่วน `--timeout 300` เผื่อไว้ให้ `/api/refresh_all`
ที่ใช้เวลาเป็นนาที

ให้รันเป็น service ถาวร: copy `deploy/manga-webapp.service` ไปที่ `/etc/systemd/system/`
(แก้ path/user ให้ตรงกับเครื่องจริงก่อน) แล้ว

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now manga-webapp
```

จากนั้นตั้ง nginx เป็น reverse proxy ไปที่ `127.0.0.1:5050` พร้อม Basic Auth ตามที่แนะนำด้านบน

### อัปเดตโค้ดบน VPS

```bash
cd /opt/Update-Manga
git pull
.venv/bin/pip install -r webapp/requirements.txt   # เผื่อมี dependency ใหม่ (เช่น Pillow)
sudo cp deploy/manga-webapp.service /etc/systemd/system/   # เฉพาะตอนไฟล์ .service เปลี่ยน
sudo systemctl daemon-reload
sudo systemctl restart manga-webapp
```

ถ้าไฟล์ `.service` บนเครื่องถูกแก้ path/user ไว้เอง อย่า copy ทับ ให้แก้เฉพาะบรรทัด `ExecStart`
ให้ตรงกับในรีโปแทน (ต้องมี `-k gthread --threads` ไม่งั้นจะไม่ได้ผลเรื่องความเร็วเลย)

### รีเฟรชอัตโนมัติเป็นระยะ

หน้าเว็บมีปุ่ม "รีเฟรชทั้งหมด" ให้กดเองได้ แต่ถ้าอยากให้ข้อมูลอัปเดตอัตโนมัติ ตั้ง cron เรียก
`webapp/refresh_cron.py` (สคริปต์นี้ยิง POST ไปที่ `/api/refresh_all` ของ service ที่รันอยู่):

```cron
*/30 * * * * /opt/Update-Manga/.venv/bin/python /opt/Update-Manga/webapp/refresh_cron.py >> /var/log/manga_refresh.log 2>&1
```

## Deploy บน Windows VPS

ต่างจาก Linux ตรงที่: ใช้ `webapp/requirements.txt` เหมือนกัน (ข้าม playwright โดยอัตโนมัติ ไม่ต้องมี
Visual C++ Build Tools), ใช้ `waitress` แทน `gunicorn` (gunicorn รันบน Windows ไม่ได้), และใช้
**Task Scheduler** แทน systemd/cron

```powershell
cd C:\Project\Update-Manga
py -m venv .venv
.venv\Scripts\activate
pip install -r webapp\requirements.txt

cd webapp
python migrate.py
copy ..\.env.example ..\.env
notepad ..\.env          # ใส่ TELEGRAM_TOKEN / TELEGRAM_CHAT_ID

python run_windows.py    # ทดสอบก่อน เปิด http://127.0.0.1:5050 ดู แล้ว Ctrl+C ปิด
```

จากนั้นตั้ง Task Scheduler 2 ตัว:

1. **รัน webapp ถาวร**: Create Task → Trigger "At startup" → Action: Program
   `C:\Project\Update-Manga\.venv\Scripts\python.exe`, Arguments `run_windows.py`,
   Start in `C:\Project\Update-Manga\webapp` → ติ๊ก "Run whether user is logged on or not"
2. **รีเฟรชอัตโนมัติ**: Create Task → Trigger "Daily", repeat every 30 minutes, indefinitely →
   Action: Program `C:\Project\Update-Manga\.venv\Scripts\python.exe`,
   Arguments `webapp\refresh_cron.py`, Start in `C:\Project\Update-Manga`

### อัปเดตโค้ดบน Windows VPS

```powershell
cd C:\Project\Update-Manga
git pull
.venv\Scripts\pip install -r webapp\requirements.txt   # เผื่อมี dependency ใหม่ (เช่น Pillow)
```

จากนั้นสั่ง Task Scheduler ให้รันงาน webapp ใหม่ (End แล้ว Run) โค้ดใหม่ถึงจะมีผล — ฝั่ง Windows
ไม่ต้องแก้ไฟล์ตั้งค่าอะไรเพิ่ม เพราะจำนวน thread ของ waitress อยู่ใน `run_windows.py` ซึ่งมากับ
`git pull` อยู่แล้ว

กันเข้าถึงจากอินเทอร์เน็ต: บล็อกพอร์ต 5050 ที่ Windows Firewall แล้วเข้าเว็บผ่าน RDP บนตัว VPS เอง
(`http://127.0.0.1:5050`) หรือถ้าอยากเข้าจากนอกบ้านด้วย แนะนำ Cloudflare Tunnel แทนการเปิดพอร์ตตรง ๆ

## แจ้งเตือน Telegram

เว็บแอปจะส่งข้อความ Telegram อัตโนมัติทุกครั้งที่ scrape แล้วเจอว่าตอนล่าสุดเปลี่ยนไปจากที่รู้ล่าสุด
(ไม่ว่าจะกดปุ่ม "รีเฟรชทั้งหมด" เอง, กด "รีเฟรช" รายเรื่อง, หรือมาจาก cron/`refresh_cron.py`) —
จะไม่แจ้งตอนเพิ่งเพิ่มเรื่องใหม่ครั้งแรก (ยังไม่มีของเก่าให้เทียบ) และ **แจ้งเฉพาะเรื่องที่บัญชี
admin ติดตามอยู่เท่านั้น** (ถ้ามีหลาย admin และมีคนติดตามอยู่อย่างน้อยคนเดียวก็แจ้ง) — เรื่องที่ผู้ใช้
ทั่วไปติดตามแต่ admin ไม่ได้ติดตามจะไม่ส่ง Telegram ให้ (Telegram ผูกกับแชทเดียวของ admin เท่านั้น)

ตั้งค่า:

1. คุย กับ [@BotFather](https://t.me/BotFather) ใน Telegram แล้วพิมพ์ `/newbot` จะได้ `TELEGRAM_TOKEN`
2. ส่งข้อความอะไรก็ได้คุยกับบอทที่สร้าง 1 ข้อความ แล้วเปิด
   `https://api.telegram.org/bot<TOKEN>/getUpdates` ในเบราว์เซอร์ จะเห็น `"chat":{"id": ...}`
   เอาเลขนั้นมาเป็น `TELEGRAM_CHAT_ID`
3. คัดลอก `.env.example` เป็น `.env` แล้วใส่ค่าทั้งสองตัวลงไป (อยู่ที่ root ของโปรเจกต์ ข้าง ๆ
   โฟลเดอร์ `webapp/` — ไฟล์ `.env` ไม่ถูก commit ขึ้น git)

ตัวแอป (`app.py`) โหลด `.env` เองอัตโนมัติทุกครั้งที่เริ่มรัน (ทั้ง dev และ production, ทั้ง Windows/Linux)
ไม่ต้อง `export`/`set` เองเลย — แค่มีไฟล์ `.env` วางไว้ที่ root ของโปรเจกต์ก็พอ รีสตาร์ทแอปหลังแก้ `.env`
ทุกครั้ง (`sudo systemctl restart manga-webapp` บน Linux service, หรือรัน task ใหม่บน Windows)

## หลายแหล่งที่มา / เว็บล่ม

เรื่องหนึ่งใส่ได้หลายแหล่งที่มา (หน้า "ตั้งค่า" → แก้ไขเรื่อง → "+ เพิ่มแหล่งที่มา") แนะนำให้ใส่อย่างน้อย 2
เว็บสำหรับเรื่องที่อ่านประจำ เพราะระบบจะสลับไปใช้แหล่งอื่นให้อัตโนมัติเวลาเว็บใดเว็บหนึ่งล่ม:

- **ตอนเปิดอ่าน** — ระบบจำลิงก์ของตอนเดียวกันจากทุกแหล่งไว้ ถ้าแหล่งหลักล่ม (เชื่อมต่อไม่ได้ / timeout /
  error 5xx เช่น Cloudflare 522, 523) จะดึงจากแหล่งสำรองแทนทันที รวมถึงกรณีที่เคยเปิดตอนนั้นไว้แล้วแต่
  เซิร์ฟเวอร์รูปของเว็บที่ล่มโหลดรูปไม่ขึ้น หน้าอ่านจะขอรูปชุดใหม่จากแหล่งสำรองให้เอง
- **จำว่าเว็บไหนล่ม 10 นาที** — เว็บที่ล่มแบบนี้มักค้างรอเกือบ 20 วิก่อนตอบ error (วัดจริงจาก 522 ของ
  slow-manga ได้ 19.6 วิ) ระบบจะรอครั้งเดียวแล้วข้ามเว็บนั้นไปก่อน ไม่ต้องรอซ้ำทุกตอน/ทุกเรื่อง
  (จำไว้ในหน่วยความจำ รีสตาร์ทแล้วเริ่มนับใหม่)
- **ตอนรีเฟรช** — แหล่งไหนล่มก็ข้ามไป ตอนใหม่จากแหล่งที่ยังดีเข้ามาตามปกติ และตอนเดิมที่มีแค่ในแหล่งที่ล่ม
  ไม่หายไปจากรายชื่อ รอเว็บกลับมาก็กลับมาเป็นปกติเอง

ข้อจำกัด: ตอนที่มีอยู่แค่ในเว็บที่ล่ม (แหล่งอื่นไม่มีตอนนั้น) ยังอ่านไม่ได้จนกว่าเว็บนั้นจะกลับมา
เว้นแต่เคยเปิดอ่านในเครื่องนั้นแล้ว (รูปยังอยู่ในแคชของเบราว์เซอร์)

## ตอนหลอก (ลงตอนใหม่ไว้เรียกยอดแต่ยังไม่มีรูป)

บางเว็บ (เช่น manga-lc.net) ลง "ตอนใหม่" ไว้ก่อนทั้งที่ยังไม่มีตอนจริง หน้าตอนมีแค่แบนเนอร์ของเว็บ 1-2 รูป
ตอนรีเฟรช ระบบจะเปิดดูข้างในตอนใหม่ก่อน ถ้ามีรูปน้อยกว่า 3 รูป (`MIN_REAL_IMAGES` ใน `app.py`)
ถือเป็นตอนหลอก:

- ไม่ขึ้นในรายชื่อตอน ไม่ขึ้น NEW และไม่ส่ง Telegram
- ตรวจซ้ำทุกรอบรีเฟรช พอเว็บอัปโหลดรูปจริงเมื่อไหร่ก็ขึ้นเป็นตอนใหม่และแจ้งเตือนตามปกติ (ครั้งเดียว)
- ถ้าใส่หลายแหล่งที่มา แล้วแหล่งหลักเป็นตอนหลอกแต่แหล่งอื่นมีตอนจริง จะใช้ของแหล่งอื่นให้เลย
- ตอนที่ตรวจผ่านถูกเก็บแคชไว้ รอบถัดไปไม่ต้องยิงซ้ำ และผู้ใช้กดอ่านตอนใหม่ได้ทันที

ข้อจำกัด: ถ้ามีเว็บไหนรวมทั้งตอนเป็นรูปยาวแค่ 1-2 รูปจริง ๆ ตอนนั้นจะถูกมองเป็นตอนหลอกไปด้วย
(เว็บกลุ่มที่รองรับอยู่ไม่มีแบบนี้ ตอนจริงมีราว 10 รูปขึ้นไป) — ถ้าเจอ ลดค่า `MIN_REAL_IMAGES` ลง

## ประสิทธิภาพ / การแคช

สรุปว่าอะไรถูกแคชไว้ตรงไหนบ้าง (เผื่อเวลาแก้โค้ดต่อจะได้ไม่เผลอทำพัง):

- **ไฟล์ static (`app.js`, `style.css`)** — `url_for` เติม `?v=<เวลาที่แก้ไฟล์>` ให้อัตโนมัติ แล้ว
  ส่ง `Cache-Control: max-age=1 ปี, immutable` แก้ไฟล์เมื่อไหร่ URL เปลี่ยนเอง ผู้ใช้ได้ของใหม่ทันที
  ไม่ต้อง hard refresh
- **รูปภาพผ่าน `/api/img`** — แคชในเบราว์เซอร์ 30 วัน และส่งต่อแบบ stream (ไม่อ่านทั้งรูปเข้า RAM ก่อน)
  พร้อมใช้ connection เดิมซ้ำกับ CDN ต้นทาง
- **รูปปก** — หน้าเว็บขอผ่าน `/api/img?...&w=400` (การ์ดในกริด) หรือ `&w=120` (รูปเล็กในหน้าตั้งค่า)
  เซิร์ฟเวอร์ย่อด้วย Pillow แปลงเป็น WebP แล้วเก็บไว้ที่ `webapp/data/covers/` ครั้งเดียว ครั้งต่อไป
  อ่านจากไฟล์ที่ย่อไว้เลย ไม่ต้องยิงไปเว็บต้นทางอีก (ปกต้นทางมักเป็นไฟล์เต็มขนาดหลายร้อย KB ทั้งที่
  การ์ดกว้างแค่ ~160px) — ถ้าไม่มี Pillow หรือย่อไม่สำเร็จ จะส่งรูปต้นฉบับแทน ใช้งานได้ตามปกติ
- **cookie ของ session** — ตั้ง `SESSION_REFRESH_EACH_REQUEST=False` ไว้ **ห้ามเปิดกลับ** เพราะถ้า
  ทุก response แนบ `Set-Cookie` ค่าใหม่มาด้วย (คู่กับ `Vary: Cookie`) เบราว์เซอร์จะถือว่ารูปที่แคชไว้
  ใช้ไม่ได้และโหลดใหม่หมดทุกครั้ง — อายุ cookie 90 วันถูกต่อให้ตอนเปิดหน้าเว็บแทน (ดู `index()`)
- **API (`/api/manga`, `/api/catalog`, ...)** — มี ETag ให้เบราว์เซอร์ถามซ้ำแล้วได้ `304` เปล่า ๆ
  ถ้าข้อมูลไม่เปลี่ยน และบีบ gzip ให้อัตโนมัติ (เล็กลงราว 80%)
- **ข้อมูลในไฟล์ JSON** — `storage.py` แคชผล parse ไว้ในหน่วยความจำ ตรวจความสดจาก mtime ของไฟล์
  (ใช้ได้ข้ามหลาย worker) ทุก request จึงเหลือแค่ `stat()` ไม่ต้อง parse ใหม่ — **โค้ดที่จะแก้ข้อมูล
  แล้วเซฟกลับต้องเรียก `load_*(fresh=True)` เสมอ** เพราะของที่ได้จากแคชเป็น object ที่แชร์กันทั้ง process
- **อัปเดตอัตโนมัติฝั่งผู้ใช้** — หน้าเว็บจำ "รหัสเวอร์ชัน" (เวลาที่แก้ `app.js`/`style.css` ล่าสุด)
  ไว้ตั้งแต่ตอนเปิด แล้วเช็คกับ `/api/version` ทุกครั้งที่กลับมาเปิดแอป ถ้าไม่ตรงจะโหลดตัวเองใหม่ให้
  อัตโนมัติ (ถ้ากำลังอ่านอยู่จะรอจนกดปิดกลับมาหน้ารวมก่อน ไม่รีโหลดขัดจังหวะ) — ผู้ใช้บนมือถือจึงไม่
  ต้องล้างแคชเองเวลามีของใหม่ ซึ่งทำได้ยากมากโดยเฉพาะตอนเพิ่มเป็นแอปบนหน้าจอโฮม
  **หมายเหตุ:** รหัสนี้คิดจากไฟล์ static เท่านั้น เพราะ `app.py` กับ `templates/index.html` ถูกอ่าน
  เข้าหน่วยความจำตอน process เริ่มทำงาน แก้แล้ว **ต้องรีสตาร์ท service/task ก่อนถึงจะมีผล**
- **หน้าเว็บ** — ข้อมูลชุดแรก (ผู้ใช้/เรื่องที่ติดตาม/ค่าตั้งค่า) ฝังมากับ HTML เลย หน้าแรกจึงขึ้นได้
  ทันทีโดยไม่ต้องรอยิง API ต่อกันหลายรอบ และหน้าอ่านจะโหลดรายการรูปของตอนถัดไปรอไว้ล่วงหน้าตอนอ่าน
  เกินครึ่งตอน (ใช้ `?peek=1` ซึ่งจะไม่มาร์คว่าอ่านแล้ว) เปลี่ยนตอนจึงไม่มีจังหวะค้างรอ

## โครงสร้างข้อมูล

- `webapp/data/manga.json` — เรื่องทั้งหมดในระบบ (catalog กลาง ใช้ร่วมกันทุกคน) + ตอนล่าสุดที่ทราบ
- `webapp/data/users.json` — บัญชีผู้ใช้ + รหัสผ่าน (hash) + สิทธิ์ admin (ไม่ commit ขึ้น git)
- `webapp/data/users/<username>/subscriptions.json` — เรื่องที่ผู้ใช้คนนั้นติดตามอยู่
- `webapp/data/users/<username>/read_state.json` — ตอนล่าสุดที่ "อ่านแล้ว" ต่อเรื่องของผู้ใช้คนนั้น
  (ไม่ commit ขึ้น git เพราะเป็นข้อมูลส่วนตัว)
- `webapp/data/read_state.json` — ไฟล์เก่าก่อนมีระบบผู้ใช้หลายคน ถ้ายังอยู่จะถูกย้ายไปเป็นของ admin
  คนแรกให้อัตโนมัติตอนรันแอปครั้งแรกหลังอัปเดต
- `webapp/data/chapters/` — cache รายการรูปของแต่ละตอนที่เคยเปิดอ่าน (ใช้ร่วมกันทุกคน)
- `webapp/data/covers/` — รูปปกที่ย่อแล้ว (WebP) สร้างอัตโนมัติ ลบทิ้งได้ทุกเมื่อ เดี๋ยวสร้างใหม่เอง
- `webapp/data/image_domains.json` — โดเมน CDN รูปภาพที่เจอจากการ scrape จริง (ใช้จำกัดสิทธิ์ image proxy)
